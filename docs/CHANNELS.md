# 通道需求清单

VIGIL 对模型通道的要求，以及当前实测可用情况。

生成时间：2026-11-05 · 探针：`node scripts/probe-live.mjs`

---

## 1. 技术要求（协议契约）

| 项 | 要求 | 为什么 |
| --- | --- | --- |
| 协议 | OpenAI `/chat/completions` 或 Anthropic `/v1/messages` | `providers/protocols.mjs` 已实现两种适配器 |
| 温度 | 支持 `temperature=0`；个别模型只收 1（已在 registry 按通道钉死） | 排出随机性，结果才可比 |
| 上下文 | ≥32k；开 `--history-window 3` 后 ≥8k 即可 | 每轮重渲染棋盘/状态/约束 |
| `max_tokens` | ≥4096；推理型 ≥16384 | 否则整轮被 `finish_reason=length` 截断，测的是上限不是能力 |
| 工具调用 | 不需要 | 动作面是纯 JSON 文本 |
| 流式 | 不需要 | 非流式聚合即可 |
| **提示词缓存** | **强烈建议** | 实测缓存命中 88–95%，是成本可承受的前提 |
| 延迟 | <10s/call 为宜 | 每格 50–90 轮 |
| 余额 | 需足够跑满一轮 | 官方 deepseek 曾在 run 中途 402 |

## 2. 模型选择（按优先级）

| 优先 | 模型 | 理由 |
| --- | --- | --- |
| **P0** | DeepSeek V4 Flash（官方） | 最便宜、支持缓存、输出简洁（84 tok/call）、延迟低 |
| **P0** | Qwen 3.8 Max / Flash（官方或 OpenCSG） | 与 DeepSeek 不同族；Flash 版本 2s 级 |
| **P1** | GLM-5.3 / 5.3-Flash（智谱官方 anthropic 端点） | 第三族；Flash 便宜 |
| **P1** | Gemini 3 Flash | 不同族（Google），但 relay 侧常被下架 |
| **P2** | MiniMax M3 / Kimi K3 | 补族；Kimi 要求 `temperature=1` |
| **不建议** | 长思考型推理模型（如 v4-pro） | 单轮输出 7k+ token，成本被输出吃掉 88× |

**为什么至少要 3 个族**：跨模型排名需要区分度。单模型只能出「深度曲线」，
不能出「谁更强」。两个模型只能出一次对比，无法判断是模型差异还是噪声。

`scripts/probe-live.mjs` 探了 **120 个 (端点, 模型) 组合**，**6 个能答话**：

| 6.9s | `glm-5.3-flash` | Agent2API (127.0.0.1:3065) |

失败分布：**97× fetch failed**（本地反代端口已死）、8× 超时、6× 返回空内容、

## 4. 需要提供什么

**最小可发布配置（1 个族）**：一个稳定、有余额、支持缓存的官方通道。
建议 DeepSeek 官方 —— 最便宜，且实测 88% 缓存命中。

**可做跨模型排名（3 个族）**：
1. DeepSeek 官方（余额）
2. 阿里云百炼 / OpenCSG 的 Qwen 3.8
3. 智谱官方 GLM-5.3（anthropic 端点）

填进 env 即可，无需改代码：

```bash
export DEEPSEEK_API_KEY=...
export SENSENOVA_API_KEY=...      # 或 OPENCSG 走本地网关
export BIGMODEL_API_KEY=...
node scripts/probe-live.mjs       # 先确认谁活着
node scripts/cluster.mjs --models deepseek:deepseek-chat,bigmodel:glm-5.3-flash ...
```

## 6. 2026-11-06 实测：为什么"用本对话的模型额度"跑不了矩阵

直接试了当前会话自己在用的通道（magpie → apigoto → `deepseek-v4.1-flash-1017`）。
它能回话，1.4 秒，输出只有 34 token——理想模型。跑批量矩阵时：

```
cells 53 · scoreable 11 · win 11 · 403 × 35 · timeout × 6 · 429 × 1
depth 8-9: 10/10 · 深度 10-12: 1/1
```

403 的原文：

> APIGOTO 云网关 (api.apigoto.com)：免费会员的免费额度仅限在 **RouterCode 客户端**中使用；
> 如需在其它工具中调用，请开启 **API 扣费访问**并保有 Credits（此类调用扣 Credits），
> 或升级付费会员。

也就是说：**免费额度绑定官方客户端，API 调用不在此列**。前 11 格能跑是因为额度还没被判定，
之后整批 403。

### 同一次尝试里另一个坑

换成允许 API 的 `agent2api/auto`，探针 2.4 秒、20 token（正常）。但批量跑时它把
**每次输出 10,000 token**（路由器换了后端到推理模型），单格 40 轮 × 10k = 40 万 token，
`tokens/s` 直接把墙钟拖到 200 秒/次。

**结论**：通道不是"有没有"的问题，是三个不稳定叠在一起：

| 不稳定 | 表现 | 对实验的影响 |
| --- | --- | --- |
| 免费额度绑客户端 | 403 `permission_error` | 批量直接死 |
| 路由器换后端 | 同一 model id 输出从 67 → 10,000 token | 成本/时长失控 |
| 模型被下架 | 404 `模型不存在` | 昨天能跑的 run 今天不可复现 |

要在本机跑出**足功效**的矩阵（≥42 格/组），需要一个**固定 model id、允许 API 扣费、
输出长度受控**的官方通道。这不是代码问题：`scripts/cluster.mjs` 已经支持
`--resume`，通道一通，一条命令接着跑完，不用改任何代码。

## 7. 2026-11-06 复测：低并发不再 403，但模型把输出预算全烧在思考上

把并发压到 `cc=3`、`pace=600ms`，同一通道跑了 `runs/deep-1`（depth 10–16，9 题）。
**29 次调用没有出现 403**——所以之前的 403 是**负载触发**，不是硬额度。

但同一批调用里 25/29 的输出恰好是 **4096 token**，即被上限截断。探针
`scripts/probe-finish.mjs` 发送真实系统提示 + 真实观测，单次调用：

| max_tokens | stop_reason | 可见文本 | thinking | 耗时 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1024 | `max_tokens` | 0 字符 | 2935 | 7.5s | 不可用 |
| 4096 | `max_tokens` | 0 字符 | 12215 | 28s | 不可用 |
| 16384 | `end_turn` | 111 字符 | 22709 | 53s | 可用（7929 输出 token） |
| 32768 | `max_tokens` | 0 字符 | 89187 | 195s | 不可用（想到上限还没想完） |

同一个提示词、同一个模型，思考长度在 **2935–89187** 之间跳。`thinking.budget_tokens`
被网关接受但**不生效**：请求 1024，实际产出 17897
（`scripts/probe-reasoning-budget.mjs`，四种取值全部如此）。

### 因此暴露了一个判分 bug（已修）

Anthropic 协议的截断标记是 `stop_reason=max_tokens`，OpenAI 是 `finish_reason=length`。
runner 只认后者，于是：

1. 推理型回复被当成正常回答；
2. 空文本走解析失败分支 `continue`，每轮再烧 4096 token，直到 `turn_cap`；
3. `turn_cap` 是**可评分**状态——一个从没产出过动作的格子会被算成「预算用尽的败局」。

修复：`providers/protocols.mjs` 统一 `max_tokens → length`；`runner.mjs` 在解析
**之前**判截断，空文本连续两次直接 `status=protocol_error`（不可评分），且
`turn_cap` 只在状态仍为 `completed` 时设置。3 个回归测试在
`test/providers.test.mjs`。

### 结论（回答「能不能用本对话模型的额度」）

**能跑通，但不能撑起足功效矩阵。** 每次决策 11–53 秒、思考长度不可控、约三成调用会
顶到上限；126 个可评分格按 cc=3 估算要 **20 小时以上**，且部分格子必然因截断作废。
它适合做**小样本试点**（`maxTokens: 16384` 已写进 registry 并附原因），不适合当主榜通道。
另：这条通道同时供给当前对话，压满会连带影响会话本身。

### harness 的应对：同轮升预算，而不是丢掉整格

`runner.mjs` 现在把「顶满输出上限」当作**这一轮没有答案**，而不是失败：

1. 截断在同一轮内重试，预算翻倍（`16k → 32k`，上限 `hardMaxTokens`，默认 32k）；
2. 重试不把截断的思考写回对话历史（否则等于偷偷改 prompt）；
3. 到上限仍截断才落 `status=truncated`，**不可评分**；
4. 账本预留用当次真实上限，`protocol.json` 记的是每通道的上限而不是写死的 4096。

单格实测（`runs/deep-3`，`rush-d12-off-s8`，6 轮上限；本地诊断 run，含 0 个可评分格）：

| 轮 | 输出 token | 思考长度 | 结果 | 耗时 |
| --- | --- | --- | --- | --- |
| t0 | 15256 | 41k 字符 | 正常出招 | ~105s |
| t1 | 16384 | 48386 字符 | 截断 → 升到 32768 | ~118s |
| t2 | 16384 | 52876 字符 | 截断 → 升到 32768 | ~110s |
| t2 重试 | 32768 | — | **仍截断** | ~240s |

3 轮、约 14 分钟、$0.048，最后 `truncated`。也就是说：**它在 depth 12 上会想到 32k
token 还不收口**，这不是「慢」，是不收敛。升预算能救回一部分轮次（t1 的重试成功出招），
但救不了这种长尾。

**最终判定**：这条通道可以支撑 `depth ≤ 10` 的小样本试点，不能支撑足功效矩阵。
`runs/deep-1`（9 格）、`runs/deep-3`（1 格）、`runs/deep-5`（depth 9）都是**本地诊断 run**，
各含 0 个可评分格，未入库；唯一可评分的试点已封成 `docs/deep-run/`（8 文件、`verify` 三重通过）。

### 同一通道在 depth 8 上是满分子（`docs/deep-run`）

按上面的判定，把试点压到 depth 8–9、16 轮上限、cc=1 跑了 3 格：

| task | 状态 | 轮数 | 有效移动 | 非法 | noop | 升预算次数 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| rush-d8-off-s2 | completed | 8 | 8 | 0 | 0 | 0 | `goal_met` |
| rush-d8-off-s50 | completed | 8 | 8 | 0 | 0 | 0 | `goal_met` |
| rush-d8-off-s100 | completed | 8 | 8 | 0 | 0 | 0 | `goal_met` |

3/3 胜，每题都用 **8 步** 解掉 depth 8 的题——即最优步数，效率 **1.00×**、浪费 **0%**。
24 次调用、6.6 分钟、$0.0434；单次输出中位数 1563 token、最大 7506，全部落在 16k 以内，
**没有触发一次升预算**。

这组数字说明两件事：

1. 通道本身可用，模型在 depth 8 上确实会下棋，而且下的最优——不是"碰巧赢"。
2. 断崖不在"能不能回话"，在**思考长度随局面爆炸**：depth 8 是 1.5k–7.5k；
   depth 9（`runs/deep-5`，`rush-d9-off-s3`）从第 0 轮起每轮都顶满 16k 并升到 32k，
   跑到第 3 轮时 32k 重试进入 5 分钟超时重试链，人工中止（未产出可评分格）；
   depth 12 连 32k 都不收口。注意 depth 是**最优步数**，不是思考难度，所以这个跳变
   不随 depth 单调——这也是为什么按深度带分层抽样是对的。

所以同一模型在同一通道上，depth 8 = 3/3 胜、效率 1.00×，depth 9 起每格成本涨 4–8 倍
且可能作废。把它们混进一张榜就是造假。
