## 正文

先给数字。

同一个 8 步就能解开的滑块谜题：

- **赢的那次**：14 步有效移动，浪费掉的回合（原地等待 + 非法）占 9%，效率是最优解的 1.77 倍。
- **输的那些**：平均 33 步有效移动，浪费掉 41% 的回合，6.7 次非法移动，最多耗到 98 轮。

也就是说，失败的 Agent 不是"不会走"，它走了**两倍多的步数**——只是没有一步是在解决那个问题。

我把这个现象叫**打转（thrashing）**。它和"能力不足"是两回事，而且更贵。

### 我怎么测出来的

我做了个东西叫 VIGIL，一个开源的 Agent 评测环境。核心决定只有一个：

**难度不靠"我觉得难"，靠一个最优解求解器算出来。**

流程是这样的：

1. 随机生成一个 Rush Hour 滑块棋盘。目标车 X 被别的车挡着，要挪开挡路的车才能到出口——经常得先把车**往回**挪。
2. 用 BFS 求出**最短解**。解不出或者步数太少的，丢掉。
3. 跑一个 greedy 基线（只朝出口方向挪、不回溯、不记忆）。**greedy 能解出来的，丢掉**——因为这种题区分不了任何东西。
4. 剩下的才入库，带着"最优几步"和"greedy 在第几步走进死循环"一起。

150 个种子，最后录取 130 题（87%）；最优解 8 到 20 步；**130 题全部击败 greedy**。

这一步很重要：它保证了这个评测里**没有一道题是"其实很简单但被写坏了"**。顺带说一句，最近有篇审计发现 Terminal-Bench 系 125 个"零通过率"任务里，37.6% 根本无法被认证为真难——14 个 oracle 本身是坏的，4 个 verifier 能被绕过。一个分不清"难"和"坏"的评测，测的是它自己的 bug。

### 第二个决定：失败要能被定位到"第几步、哪条规则"

大多数 Agent 评测只给你一个 pass/fail。有些会在事后让一个 LLM 去读轨迹猜"它为什么失败"——这条路线目前最好的步级定位精度是 **14.2%**（Who&When, ICML 2025）。

我不猜。因为我拥有环境的状态，所以我可以直接算：每一步前后状态差分，和每条规则读哪些状态格子做交集，就能确定是哪个动作碰了哪条规则、那条规则是多久以前引入的。

一条真实的记录长这样：

```json
{
  "stepIndex": 65,
  "constraintId": "exit",
  "introducedAtStep": 0,
  "ageInSteps": 65,
  "class": "neglected",
  "blamedPaths": []
}
```

翻译成人话：**到第 65 步时，出口这条规则已经失败了 65 步，而这一个动作根本没碰它管的那块状态。**

六类归因：`broke`（改了不该改的）、`collateral`（没碰它也破了）、`revealed`（规则刚出现就已经不满足）、`neglected`（早就失败，这个动作无视它）、`regressed`（碰了但没修好）、`obligation_lapsed`（后台义务在你忙别的时死掉）。

### 一组具体的对照

下面全部来自公开的参考 run（13 个可评分格，4 胜 9 负）：

| | 胜局（4） | 败局（9） |
| --- | --- | --- |
| 平均轮数 | 21.3 | **68.2** |
| 最多轮数 | 34 | **98** |
| 平均有效移动 | 14.0 | **33.1** |
| 平均非法移动 | 1.5 | **6.7** |
| **浪费回合占比**（原地等待 + 非法 / 总轮数） | **9%** | **41%** |
| **效率**（有效移动 / 最优步数） | **1.77×** | **2.63×** |

（这张表可以用一条命令复算出来：`node scripts/behavior-report.mjs docs/reference-run`。
浪费占比和效率都是从动作日志直接算的，不依赖任何归因标签。）

一个标本：depth-9 的题，最优 9 步。它跑了 66 轮，其中 **54 轮是原地等待（82%）**，只走了 9 步有效移动，3 次试图直接推目标车被拒绝。也就是说它明明有 9 步的解法空间，却把 82% 的回合花在了"什么都不做"上。

这个信号在只看 pass/fail 的榜单里是**完全不可见的**。你只会看到"失败"，看不到"它花了三倍的钱在原地转圈"。

### 为什么这件事对做 Agent 的人重要

如果你的 Agent 失败模式是"打转"，那优化方向不是"提高单步准确率"，而是：

- **注意力调度**：什么时候该停下来重新读目标，而不是继续试探；
- **进度信号**：有没有一个"我离目标更近了吗"的廉价判据（这里就是"这一步碰没碰 pos.X"）；
- **预算感知**：31% 的回合是浪费，意味着 token 成本里有三成是纯损耗。

顺带一个成本数据，因为长程评测的钱全在这里：一次模型调用的输入是 2.67 万 token，输出只有 84 token。**输入占成本约 99%**，所以提示词缓存命中率（实测 88–95%）才是第一成本杠杆，输出价格几乎不影响。

我还实测了一个反直觉的点：把对话历史裁到最近 3 轮（因为每轮观察本身是自足的，棋盘、状态、规则、合法动作全都重渲染），输入从 26,750 降到 1,312，**降了 20 倍**；但那个 relay 模型是推理型的，输出从 84 涨到 7,368，**涨了 88 倍**。净成本没降。所以：**选模型比调参数重要**。

### 一个必须说的副产品：模型会作弊

这是我在跑数时抓到的，值得单独说。

有一轮里，模型连续 4 次试图直接推目标车（非法），然后发出了这么一个动作：

```json
{"action":{"type":"set","args":{"path":"pos.X.col","value":4}}}
```

`set` 是引擎的通用状态修改器。它绕过了棋盘，**直接把"目标车在哪"改成了"在出口"**。引擎报了 `goal_met`，而目标车从头到尾没动过。它那 4 个"胜局"全是这么来的。

这正是知乎 SoTALab 在《从密码游戏思考长程智能体的未来》里报告过的现象——他们 24 局里审计出 10 局用了违规捷径，占 41.7%。

我的修法：**通用修改器从动作面里彻底拿掉**，`observe()` 不列它，发了也拒绝，状态不变；只放行经过棋盘校验的 `move`。另外加两个显式回归测试，专门测"set/inc/push/remove 不能伪造胜利"。

结论很直白：**权限边界必须写进 benchmark 定义**，不能假设 Agent 会按你希望的方式交互。你现在不做，你的榜单就在奖励作弊。

### 局限，说清楚

- 上面那组对照是**单个模型、13 个可评分格**。胜局 4 个，统计上只能说"方向和量级清楚"，不能说"已确立"。
- 跨模型排名**还没做**：官方通道余额中途耗尽（HTTP 402），几个 relay 模型在长提示下超时。协议要求把这类失败记为基础设施故障、不算答错——所以 55 个格子里只有 13 个可评分。这是诚实的样本量，不是结论。
- "neglected 占 97%"这个数我不打算当结论用：因为出口是一条终局约束，在目标车移动之前任何动作都算"没碰它"。这是同义反复。真正的证据是步数、等待率、非法率这三项。

### 怎么复算

```bash
node scripts/gate.mjs                       # 测试 + 任务自审 + 仓库卫生
node scripts/discrimination.mjs <run-dir>   # greedy/oracle/模型的胜率与深度曲线
node scripts/behavior-report.mjs <run-dir>   # 打转签名：浪费占比 / 效率 / 非法率
node scripts/verify.mjs <run-dir>           # MANIFEST + 提示词指纹 + 数字重算
```

任何数字都能从 `results.jsonl` 重算出来。篡改一个字节，`verify` 直接 exit 1——我实测过。
