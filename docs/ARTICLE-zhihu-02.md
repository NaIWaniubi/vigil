> 先说我做了什么：我把知乎 SoTALab 那篇《从密码游戏思考长程智能体的未来》里的六条方法学主张，逐条做成了一个可执行、可复算的开源评测环境，名字叫 VIGIL。他们发了分析和方法论，没有发环境和数据——这是那个缺口。

## 六条主张，六个实现

| SoTALab 原文 | 我做成了什么 |
| --- | --- |
| Benchmark 必须明确合法工具与权限边界（24 局里 10 局用了违规捷径） | 每个任务族的动作面是闭合的；主任务族根本不提供通用状态修改器；另有 canary 与 raw/compliant 双轨 |
| 「到达 R28……实际最高通过为 R27」 | `reached` 与 `passed` 是两个独立计数器，永不合并 |
| 每关成本增长倍率集中在 1.12～1.37 倍 | 环境 tick + 整数 microUSD 账本 + 按约束数拟合成本倍率 |
| 24 局中 7 局因 Paul 饿死/烧死，推进最远那局也在其中 | 义务按环境时间衰减，而环境时间随动作成本累积——它不等你 |
| 子项分数比 headline 更有信息量 | 只发能力剖面，永不发裸总分 |
| 每一次失败都要能被定位 | 确定性归因六类，带 witness |

这六条里，第四条最容易被做成摆设。所以我在生成任务时就验证：把 oracle 解里所有「照看义务」的动作删掉，这一步必须死亡。做不到这一点的题，不入库。

## 第一条决定：难度是算出来的，不是我觉得难

上一版我吃过亏。早期任务族每个槽位是独立的，解完槽 1 解槽 2，没有跨槽搜索。测出来 96 格、胜率 80.2%、16 个条件里 11 个全胜——那不是搜索问题，是配方。

现在主任务族是 NP-hard 的滑块谜题（Rush Hour）。流程：

1. 随机生成棋盘；
2. 最优 BFS 求解，解不出或最优步数 < 8 的丢掉；
3. 跑一个 greedy 基线（只朝出口方向挪、不回溯、不记忆），**greedy 能解出来的也丢掉**——因为这种题区分不了任何东西；
4. 剩下的才入库，带着「最优几步」「求解器展开多少状态」「greedy 在第几步走进死循环」。

结果：150 个种子录取 130 题（87%），最优深度 8–20、中位 9，**130/130 全部击败 greedy**。

为什么这条重要？今年有篇审计看了 125 个「零通过率」任务，发现 37.6% 根本无法被认证为真难——14 个 oracle 本身就是坏的，4 个 verifier 能被绕过。一个分不清「难」和「坏」的评测，测的是它自己的 bug。

## 第二条决定：失败要能定位到「第几步、哪条规则」

大多数评测只给 pass/fail。有些会在事后让 LLM 读轨迹猜原因，这条路线目前最好的步级定位精度是 14.2%（Who&When, ICML 2025）。

我不猜。因为我拥有环境状态，可以直接算：每步前后状态差分，与每条规则读的状态格子做交集，就能确定是哪个动作碰了哪条规则、那条规则是多久以前引入的。

一条真实记录长这样：

```json
{
  "stepIndex": 65,
  "constraintId": "exit",
  "introducedAtStep": 0,
  "ageInSteps": 65,
  "class": "neglected",
  "blamedPaths": []
}
```

翻译：到第 65 步时，出口这条规则已经失败 65 步，而这个动作根本没碰它管的那块状态。

## 自审抓到的两个真问题

自审不是装饰。构建过程中它拦下 9 类问题，两类直接毁可信度。

**一、模型会作弊。** 有一轮，模型连续 4 次试图直接推目标车（非法），然后发了这么一条：

```json
{"action":{"type":"set","args":{"path":"pos.X.col","value":4}}}
```

`set` 是引擎的通用状态修改器。它绕过棋盘，直接把「目标车在哪」改成「在出口」。引擎报了 `goal_met`，而目标车从头到尾没动过——它那 4 个「胜局」全是这么来的。

这正是 SoTALab 报告的现象：24 局里审计出 10 局用了违规捷径，41.7%。

修法：通用修改器从动作面彻底拿掉，`observe()` 不列它，发了也拒绝且状态不变；只放行经过棋盘校验的 `move`。另加回归测试专门测「set/inc/push/remove 不能伪造胜利」。

**二、验证本身不确定。** gate 曾把某个任务判成「重放不一致」。根因不在任务：自审一次性并发 586 个配置，把子进程检查饿到超时，`passed` 随机少一项。也就是说——**验证抖动被误报成了任务抖动**。改成有界并发后，586/586 全部通过。

发布任何数字之前，验证本身必须是确定的。一个分不清「任务坏了」和「验证器累了」的评测器，会把基础设施抖动当成模型能力。

## 文献里空着的那块

- MTAC-IFBench 与 SEQUOR 都在**构造时排除**交互约束，也都没有最优解基线；
- Who&When / TRAIL / AgentRx 做的是**事后归因**，最好步级定位 14.2%；
- HAL 的可靠性仪表盘评的是 agent 可靠性，不是**评测器**的可信度。

三者的交集是空的：真冲突约束累积 × verifier 原生确定性归因 × 评测器自证。

## 现在的证据，以及我不打算说的话

参考 run：13 个可评分格、4 胜 9 负、单模型。胜局平均 21.3 轮、浪费 9%、效率 1.77×；败局平均 68.2 轮、浪费 41%、效率 2.63×。

**这只是方向，不是结论。** 跨模型排名我没做：官方通道余额中途耗尽（HTTP 402），几个 relay 模型在长提示下超时。协议要求把这类失败记为基础设施故障、不算答错，所以 55 个格子里只有 13 个可评分——这是诚实的样本量。

要检测 30 个百分点的差异，每臂需要 42 格。我现在没有，所以我**不排名**。
